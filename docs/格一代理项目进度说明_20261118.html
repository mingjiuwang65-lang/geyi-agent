三、客户机直接装 IA 用独立 PIN 的可行性评估

结论（明确判断）：不可行，且不建议尝试。不需要给客户机分配 180.18.8 段 IP，也不需要虚拟机装透明代理——这两条路一条走不通、一条是已实测否决的废弃方案。客户机保持内网 IP、装格一代理客户端连节点（现状方案）是唯一经过验证的路径；若客户确需独立 PIN / 独立出口，正确做法是给他独占一台节点，而不是把 IA 装到客户机上。

1. 三条架构硬约束（已实测坐实，不可绕过）

#约束证据与含义
1CPE 只放行 IA 认证流量到海外11-16 两次实测：普通 IP 流量（哪怕源地址是 .2）访问 baidu/github 通，但 google/youtube 超时；只有 IA 隧道内流量能上海外。任何"不跑 IA 就想出海"的转发/NAT 方案都不成立。
2IA 认证与 180.18.8 段 CPE 客户地址绑定移动按 CPE 客户地址放行，每台"服务器"配一个独立 180.18.8.x，网关 180.18.8.1。客户机在内网 192.168.50.x / 10.0.x，源 IP 不在该段，IA 会话无法建立或无法被 CPE 放行。
3PIN 只有 Windows 版上网助手Linux 上跑不了 IA（王工明示）。即便客户机是 Windows 能装 IA，"约束 2"的地址绑定仍是硬门槛。

2. 四种方案对比

方案可行性判断依据
A. 客户机直装 IA + 独立 PIN + 分配 180.18.8.x IP 不可行 需把办公 PC 二层接入移动 CPE 段（CPE 在机房、客户机在办公区，物理/VLAN 不现实）；一个 PIN 对应一个 CPE 地址，等于把节点资源让给 PC；CPE 网关成单点；公网 IP 直接挂在办公 PC 上，暴露面与合规风险极高。概率 evaluation：除非移动额外开通 + 二层打通，否则 < 10%，且成本远超收益。
B. 客户机装 IA + 透明代理 VM（SNAT 到 180.18.8.x） 已否决 即已废弃的 A 路（宿主机抢 .2 + SNAT）/ VM201 NAT 方案。实测回程不对称路由、认证流量与普通流量混淆，google/youtube 不通。重新实现等于走回死路，成功率 0%。
C. 客户机保持内网 IP，装格一代理客户端连节点（现状） 已验证 客户机到 5 节点 15888/15889 全通、主防火墙无限制；CA 两级验签、5 节点任选/自动切换均实测可用。IA 与 180.18.8.x 全部留在节点侧，客户机零公网暴露。
D. 为特定客户独占一台节点（克隆 VM + 独立 PIN + 独立 180.18.8.x） 可行 克隆一台 Windows VM（195/196 冷备流程已跑通），配独立 CPE IP + 独立 PIN，客户机仍装客户端连这台专属节点。满足"独立 PIN/独立出口/独占带宽"，且不动现有架构。成本：一台 VM + 一个 CPE IP + 一个 PIN。

3. 对王工两个直接提问的回答

  • "需要虚拟机装透明代理吗？" —— 不需要。透明代理 VM 本质是方案 B，已被实测否决；且现有节点本就是"透明代理网关"，客户机装客户端即可，无需再叠一层。
  • "给客户机分配一个 180.18.8 段 IP 才行吗？" —— 只有在方案 A（客户机自己跑 IA）里才"必须"，但那条路整体不可行；走现状方案 C 或独占节点方案 D，客户机完全不需要 180.18.8 段地址，保持 192.168.50.x 即可。
推荐决策：客户机一律走方案 C；领导/领导指定客户要"独立通道"，走方案 D（独占节点），不走 A/B。若坚持要评估 A，前置条件是移动书面确认「可为办公 PC 单独开通 CPE 客户地址且允许二层延伸」——在此之前不投入实施。
